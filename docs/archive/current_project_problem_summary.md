# 현재 프로젝트 문제 정의 및 정리

## 문서 목적
이 문서는 지금까지의 대화를 바탕으로, 현재 진행하려는 자동화 프로젝트의 핵심 문제를 정리한 문서다.  
목적은 아이디어를 더 늘리는 것이 아니라, **지금 무엇이 문제인지 명확히 보고 우선순위를 다시 잡기 위한 기준 문서**를 만드는 데 있다.

---

# 1. 현재 프로젝트의 본질

지금 만들고 싶은 것은 단순한 이미지 생성 툴이 아니다.  
의도한 방향은 다음과 같다.

- 이벤트 또는 캠페인 단위로 작업이 시작된다.
- 기획, 카피, 이미지 제작, 채널별 콘텐츠 제작이 이어진다.
- Midjourney 같은 이미지 생성 툴을 활용해 후보 이미지를 만든다.
- 관리자가 후보를 보고 선택한다.
- 선택된 이미지를 Figma 템플릿과 연결한다.
- 최종적으로 인스타, 블로그, 스레드, 트위터, 브런치 등 매체별 콘텐츠가 나온다.
- 이 전체 흐름이 반복 가능한 구조로 쌓여야 한다.

즉, 목표는 “이미지 1장 자동 생성”이 아니라  
**브랜드/이벤트 운영을 구조적으로 자동화하는 시스템**이다.

---

# 2. 현재 가장 큰 문제

## 문제 1. 너무 많은 것을 한 번에 하려고 했다
현재 가장 큰 문제는 범위가 너무 넓다는 점이다.  
처음부터 아래 모든 것을 한 프로젝트 안에 넣으려고 했다.

- 이벤트 브리프 생성
- 콘텐츠 기획 분기
- 이미지 프롬프트 생성
- Midjourney 후보 제작
- 관리자 선택
- Figma 조립
- 카드뉴스 제작
- 커뮤니티/그래픽 이미지 제작
- 채널별 파생 산출물 생성
- QA 및 패키징
- 자산 저장 및 재사용

이렇게 되면 구조는 멋있어 보이지만, 실제로는 어디서부터 구현해야 하는지 अस्पष्ट해진다.  
즉, **전체 그림은 있으나 실제로 굴릴 첫 단위가 너무 크다.**

---

## 문제 2. ‘하나의 거대한 자동화’로 보고 있었다
처음에는 하나의 명령 또는 하나의 큰 워크플로우로  
기획부터 이미지 제작, 카드뉴스, 채널별 확장까지 전부 이어지는 시스템을 تصور했다.

하지만 실제로는 각 단계의 성격이 다르다.

- 브리프는 기획 문제
- 이미지 생성은 후보 생산 문제
- 관리자 선택은 판단 문제
- Figma 조립은 레이아웃 문제
- 채널별 파생은 운영 규칙 문제

즉, 이 프로젝트는 하나의 기능이 아니라  
**여러 개의 작은 자동화 모듈이 연결된 운영 구조**로 봐야 한다.

---

## 문제 3. AI가 해주는 부분과 시스템이 고정해야 하는 부분이 섞여 있다
현재 구상에서는 Claude나 다른 AI가 여러 단계를 유연하게 처리하는 방향이 강했다.  
하지만 실제 프로젝트에서 모든 단계를 AI 판단에 의존하면 문제가 생긴다.

예:
- 같은 입력인데도 결과가 계속 달라질 수 있음
- 출력 포맷이 단계마다 흔들릴 수 있음
- 다음 단계에서 결과를 안정적으로 읽기 어려움
- 재실행 시 통제가 어려움

즉, **AI가 맡아야 할 영역과 규칙으로 고정해야 할 영역이 아직 분리되지 않았다.**

구분하면 대략 이렇다.

### AI가 맡는 것이 적합한 영역
- 브리프 요약
- 카피 초안
- 프롬프트 제안
- 채널별 문구 스타일 변형
- 이미지 방향 제안

### 규칙으로 고정해야 하는 영역
- 파일명 구조
- 채널 규격
- 카드뉴스 장수 구조
- 상태값 관리
- 선택 결과 저장 형식
- 템플릿 적용 방식
- QA 체크 항목

---

# 3. 현재 구조에서 특히 막힐 가능성이 큰 지점

## 문제 4. Midjourney 후보 생성 이후 흐름이 아직 추상적이다
“이미지 생성 → 관리자가 선택 → 선택본 활용”이라는 큰 방향은 맞다.  
하지만 구체적으로는 아직 부족하다.

부족한 점:
- 후보 이미지를 몇 장 만들지
- 어떤 기준으로 후보를 묶을지
- 표지용/상세용/배너용을 어떻게 구분할지
- 텍스트 삽입 여백을 어떻게 판단할지
- 후보 메타데이터를 어떻게 붙일지

즉, **이미지 생성 단계는 정의되어 있지만 운영 구조는 아직 약하다.**

---

## 문제 5. 관리자 선택 단계가 개념 수준에 머물러 있다
관리자가 중간에 선택해야 한다는 인식은 매우 정확하다.  
하지만 선택 단계가 실제 시스템으로 정의되지는 않았다.

아직 정리되지 않은 것:
- 어떤 UI에서 선택할지
- 선택 / 제외 / 재생성 요청을 어떻게 기록할지
- 선택 이유를 남길지
- 선택 결과를 다음 단계에 어떤 포맷으로 전달할지
- 버전 관리를 어떻게 할지

즉, **관리자 선택은 중요하다고 알고 있지만, 시스템의 기능 단위로는 아직 설계되지 않았다.**

---

## 문제 6. Figma 조립 단계가 생각보다 훨씬 중요하지만 아직 구체적이지 않다
처음에는 AI 생성이나 프롬프트 쪽에 시선이 많이 갔지만, 실제 실무 완성도는 Figma 조립에서 결정된다.

실제로 필요한 것:
- 카드뉴스 템플릿 구조
- 각 장의 역할 정의
- 텍스트 길이 대응 방식
- 이미지 비율이 달라도 버티는 레이아웃
- CTA 위치 규칙
- 채널별 리사이즈 규칙

즉, **좋은 이미지를 만드는 것보다 좋은 템플릿 시스템을 만드는 것이 더 중요하다.**

---

## 문제 7. ‘예쁜 이미지’와 ‘편집 가능한 이미지’가 아직 구분되지 않았다
이미지가 잘 나왔다고 해서 바로 쓸 수 있는 것은 아니다.  
실제 운영에서는 아래 조건이 중요하다.

- 텍스트가 들어갈 공간이 있는가
- 표지로 쓸 수 있는가
- 카드뉴스 상세 장에도 어울리는가
- 여러 채널로 변형 가능한가
- 브랜드 톤과 맞는가

즉, **이미지 퀄리티와 운영 적합성은 다른 문제**다.  
이 판단 기준이 프로젝트 안에 더 명확히 들어가야 한다.

---

# 4. 채널 전략 측면의 문제

## 문제 8. 채널별 분기 규칙이 아직 명확하지 않다
현재 목표 채널은 매우 많다.

- 인스타
- 스레드
- 트위터
- 네이버 블로그
- 브런치
- 커뮤니티/공지형 콘텐츠

하지만 아직 각 채널별로 아래가 명확하지 않다.

- 어떤 형식이 기본인지
- 어떤 문구 길이를 쓰는지
- 어떤 이미지 유형이 필요한지
- 어떤 채널은 감도 중심인지, 어떤 채널은 정보 중심인지
- 어떤 채널은 단일 이미지인지, 어떤 채널은 시퀀스형인지

즉, **채널 이름은 정해졌지만 채널별 운영 규칙은 아직 제품화되지 않았다.**

---

## 문제 9. 한 이벤트에서 매체별 콘텐츠를 뽑고 싶지만, 공통 원본 구조가 아직 약하다
원하는 방향은 하나의 이벤트에서 여러 채널용 콘텐츠를 파생하는 것이다.  
이 방향은 맞다.

하지만 그러려면 모든 채널이 공유하는 공통 원본이 필요하다.

예:
- 핵심 메시지
- 이벤트 목적
- 타깃
- CTA
- 브랜드 톤
- 선택된 핵심 비주얼

이 공통 원본이 약하면 매체별로 결과가 따로 놀게 된다.  
즉, **멀티채널 자동화 이전에 공통 원본 구조가 더 단단해야 한다.**

---

# 5. 운영 시스템 관점에서의 문제

## 문제 10. 상태 관리 개념이 부족하다
현재는 폴더 구조나 단계 구상은 있지만, 실제 운영 시스템처럼 “상태”가 정의되지는 않았다.

필요한 상태 예시:
- draft
- brief_done
- planning_done
- image_generating
- selection_pending
- figma_pending
- qa_pending
- complete

이런 상태가 없으면 이벤트가 많아졌을 때 무엇이 어디까지 진행됐는지 알기 어렵다.  
즉, **파일 저장 구조만으로는 운영이 안 되고, 상태값 관리가 필요하다.**

---

## 문제 11. 결과물보다 자산화 구조가 덜 보인다
지금 프로젝트는 결과물 생성 쪽 아이디어가 풍부하다.  
하지만 장기적으로 더 중요한 것은 자산 축적이다.

필요한 자산:
- 잘 먹힌 프롬프트
- 채택된 이미지 유형
- 채널별 성공 카피 패턴
- 이벤트 유형별 카드뉴스 구조
- 브랜드별 템플릿
- 재사용 가능한 CTA 세트

즉, 이 프로젝트는 한 번 쓰고 끝나는 자동화가 아니라  
**운영 자산을 계속 쌓는 시스템**이 되어야 한다.

---

## 문제 12. 테스트 기준이 아직 부족하다
본인 브랜드보다 메이저 브랜드로 테스트해보자는 방향은 맞다.  
하지만 아직 테스트 기준표가 정리되진 않았다.

필요한 기준:
- 톤 일치도
- 비주얼 일관성
- 텍스트 삽입 안정성
- 채널별 변형 적합성
- 선택 단계의 효율성
- 템플릿 재사용성

즉, **무엇을 테스트할지보다 어떻게 성공/실패를 판단할지가 더 먼저 필요하다.**

---

# 6. 현재 방향을 어떻게 다시 잡아야 하는가

## 핵심 전환 1. 하나의 큰 자동화가 아니라 작은 자동화 3~5개로 쪼개야 한다
현재 가장 필요한 전환은 이것이다.

기존 시각:
- 하나의 이벤트 자동화 시스템

바꿔야 할 시각:
- 여러 작은 자동화 모듈이 연결된 구조

예시 모듈:
1. 이벤트 브리프 생성 모듈
2. 인스타 카드뉴스 제작 모듈
3. 블로그 썸네일/본문 이미지 모듈
4. 커뮤니티 공지 이미지 모듈
5. 자산 관리 모듈

이렇게 쪼개야 실제로 설계하고 만들 수 있다.

---

## 핵심 전환 2. 모듈끼리 회사처럼 구조적으로 연결되어야 한다
모듈을 나누는 것만으로는 부족하다.  
서로 다른 모듈이 공통 데이터를 공유해야 한다.

공유해야 할 것:
- 브랜드 가이드
- 이벤트 브리프
- 핵심 메시지
- 금지어
- 선택된 이미지 자산
- 승인 상태

즉, **‘작은 자동화’와 ‘하나의 운영 구조’가 동시에 있어야 한다.**

---

## 핵심 전환 3. 바로 구현보다 워크프레임과 와이어프레임이 먼저다
지금 단계에서는 기능을 바로 붙이기보다,  
먼저 아래를 정리해야 한다.

- 전체 시스템 맵
- 모듈 구성도
- 정보 구조(IA)
- 상태 흐름
- 모듈별 화면 역할
- 관리자 선택 UI
- 결과물 저장 구조

즉, 지금은 개발보다  
**워크프레임 → UI/UX 와이어프레임 → 시스템 설계**가 먼저다.

---

# 7. 지금 시점에서 가장 적절한 실행 방향

## 우선순위 1. 범위를 줄인다
처음부터 모든 채널을 다 하려고 하지 않는다.  
예를 들어 1차 범위는 이렇게 줄일 수 있다.

- 이벤트 브리프
- 인스타 카드뉴스
- 블로그 썸네일
- 이미지 후보 선택
- 간단한 자산 저장

---

## 우선순위 2. 모듈을 먼저 정한다
지금은 전체 기능보다 먼저 “몇 개의 자동화 모듈로 쪼갤지”를 정해야 한다.

권장 예시:
- 브리프 모듈
- 인스타 모듈
- 블로그 모듈
- 커뮤니티 모듈
- 자산 모듈

---

## 우선순위 3. 모듈별 와이어프레임을 만든다
와이어프레임은 예쁜 화면보다 역할이 중요하다.

예시:
- 브리프 화면 = 방향 정리
- 이미지 후보 화면 = 선택
- 카드뉴스 조립 화면 = 확인 및 수정
- 자산 화면 = 저장 및 재사용
- 대시보드 = 상태 확인

---

## 우선순위 4. 메이저 브랜드로 테스트한다
본인 브랜드보다 운영 레퍼런스가 강한 메이저 브랜드를 기준으로 테스트해야 한다.  
이유는 브랜드 톤, 운영 방식, 시각 규칙을 비교하기 쉽기 때문이다.

즉, 지금 단계는 브랜드 구축보다 **시스템 검증 단계**에 가깝다.

---

# 8. 한 줄 결론

현재 프로젝트의 핵심 문제는  
**아이디어가 부족한 것이 아니라, 너무 많은 좋은 아이디어를 한 번에 담으려 해서 실제 첫 실행 단위가 불명확해진 것**이다.

따라서 지금 필요한 것은 더 많은 기능 추가가 아니라 아래 네 가지다.

1. 범위 축소  
2. 작은 자동화 모듈로 분해  
3. 모듈 간 연결 구조 설계
